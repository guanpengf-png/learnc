# 小白调试入门（大白话版）

你写完程序，一跑就崩、结果不对，又不想瞎猜——这时用「调试器」最好。

调试器就像给程序装了「慢放 + 暂停键」：

- 可以在某一行 **停住**
- 可以 **一步一步** 往下跑
- 可以随时 **偷看变量里是什么**

---

## 和一般说的 debug 有啥区别？

日常说的「debug」，很多时候其实是这种：

```c
printf("到这里了\n");
printf("size = %zu\n", b->size);
```

跑一遍，看终端打印，猜问题在哪，改代码，再编译再跑。  
这叫 **打印调试（printf debug）**，也是「一般的 debug」。

而本教程说的，是用 **调试器（debugger）**，比如 `lldb` / `gdb`。  
目标一样——找 bug，但干活方式不一样。

### 一句话对比

| | 一般 debug（printf） | 调试器（lldb/gdb） |
|--|----------------------|---------------------|
| 怎么观察 | 事先在代码里埋 `printf` | 程序跑着随时暂停、偷看 |
| 要不要改源码 | 经常要改，查完还得删 | **不用改业务代码** |
| 能看多少 | 你打印啥才能看啥 | 停住后几乎所有变量都能看 |
| 控制运行 | 只能「整段跑完」 | 能断点、单步、一步步跟 |
| 崩的时候 | 往往只看到 `Segmentation fault` | 能停在出事附近，还能看调用栈 |
| 适合场景 | 小问题、逻辑很清楚时 | 指针、链表、内存池、莫名崩溃 |

### 大白话打个比方

- **一般 debug**：像给快递员一路贴便利贴——「我到了门口」「我上了楼」。你只能看到纸条上写的那几句。  
- **调试器**：像给你一个遥控器——随时暂停、快进一格、打开包裹看里面是什么。

### 各自擅长什么

**printf 调试好在哪：**

- 上手快，不用学新工具  
- 有些问题「跑很长一段时间才出现」，打日志反而方便事后翻  
- 交作业、演示时偶尔留几行日志也正常  

**它烦在哪：**

- 漏打了关键变量，就得改代码 → 重新编译 → 再跑，来回很磨人  
- 指针、链表、内存布局，靠打印很容易漏、也很难读  
- 程序一崩溃，后面的 `printf` 可能根本来不及输出  

**调试器好在哪：**

- 不污染代码：查完断点一撤就行  
- 适合看「某一刻内存到底长什么样」（内存池、`Block*`、空闲链特别合适）  
- 崩溃时往往能直接带你到附近，再用 `bt` 看是谁一层层调用过来的  

**它烦在哪：**

- 要先会几个命令（本教程后面就会教）  
- 交互程序、死循环、多线程时，刚开始可能有点懵（先从单文件小程序练）

### 所以该怎么选？

不用站队，**两种都是正经手段**：

1. **先会 printf**：确认「大概错在哪一段」  
2. **再上调试器**：对准那一段下断点，把指针、结构体、链表状态看清楚  

对咱们这个内存池项目：分裂、合并、空闲链——用调试器盯着 `*b`、`phys_next`，比刷一屏幕 `printf` 舒服得多。

> 记住：一般说的 debug =「找 bug 这件事」；  
> `lldb`/`gdb` =「找 bug 时用的专业暂停工具」。  
> 一个是目标，一个是更强的工具。

## 0. 先说清楚：你电脑上用哪个？

| 工具 | 你这台 Mac |
|------|------------|
| `gdb` | 默认 **没有**，要自己 `brew install gdb`，还可能要签名，比较折腾 |
| `lldb` | **系统自带**，直接能用 |

**结论：先学 `lldb`。**  
命令名字和 `gdb` 几乎一样（`b`、`run`、`n`、`p`……），以后换 `gdb` 也不慌。

下面全程用 `lldb`，拿咱们的内存池练手。

## 1. 开始前必须做的两件事

### ① 编译时要带调试信息（`-g`）

没有 `-g`，调试器就像「地图没标注」，断点、变量名经常对不上。

我们这个项目的 Makefile 已经写好了：

```bash
cd day7/mempool
make clean
make
```

看到命令里有 `-g` 就对了。

### ② 进目录，启动调试器

```bash
cd day7/mempool
lldb ./mempool
```

成功的话，你会看到类似：

```text
(lldb)
```

这个小括号提示符，表示：**调试器已经接管，在等你下命令。**

想退出随时输入：

```text
q
```

再按一次确认退出就行。

## 2. 最核心的 6 个命令（先背这几个）

| 你想干什么 | 敲什么 | 大白话 |
|------------|--------|--------|
| 在某函数停下 | `b pool_alloc` | 程序跑到 `pool_alloc` 就 **暂停** |
| 在某行停下 | `b mempool.c:289` | 跑到这个文件第 289 行就停 |
| 开始跑程序 | `run` | 按「播放」；带参数就 `run -i` |
| 一行行往下（不钻进函数） | `n` | next，像「下一句」 |
| 一行行往下（会钻进函数里面） | `s` | step，像「走进去看」 |
| 继续跑到下一个断点 | `c` | continue，解除暂停 |
| 看某个变量 | `p cur` / `p *cur` | print；加 `*` 是看指针指向的内容 |
| 我现在卡在哪 | `bt` | backtrace，看调用栈（谁叫谁） |

记口诀：

> **先 `b` 下断点 → `run` 跑起来 → 停住后用 `n`/`p` 观察 → 看完 `c` 继续**

## 3. 跟着做一遍（推荐）

下面按「第一次调试」完整走一遍。终端里复制粘贴也行。

### 第 1 步：启动

```bash
cd day7/mempool
make
lldb ./mempool
```

### 第 2 步：在「分裂空闲块」函数打断点

```text
(lldb) b block_split
```

大概会提示：Breakpoint 1: ...

意思是：**以后程序一进 `block_split`，就自动停住。**

再加一个合并的断点也行：

```text
(lldb) b block_coalesce
```

### 第 3 步：跑起来

```text
(lldb) run
```

程序会正常开始演示；第一次分配大块、需要切开时，就会停在 `block_split`。

### 第 4 步：停住以后看一眼

```text
(lldb) f
```

`f`（frame）会告诉你：现在停在哪一行。

再看参数：

```text
(lldb) p need
(lldb) p b->size
(lldb) p *b
```

- `p need`：用户这次要多少字节  
- `p b->size`：这块空闲区现在有多大  
- `p *b`：把整个块头结构打印出来（`is_free`、`phys_next` 等）

### 第 5 步：单步看看分裂怎么发生

```text
(lldb) n
```

多按几次 `n`，看着代码往下走。  
当你觉得「新块 `n` 应该造好了」，再：

```text
(lldb) p *n
(lldb) p b->size
```

对比一下：原来一大块，是不是变成「前面 need、后面剩余」了。

### 第 6 步：继续跑，去看合并

```text
(lldb) c
```

后面释放内存时会进 `block_coalesce`，再次停住。同样：

```text
(lldb) p *b
(lldb) p b->phys_next
(lldb) n
```

看左右邻居是不是空闲、size 会不会变大。

### 第 7 步：看完退出

```text
(lldb) q
```

## 4. 交互模式怎么调？

内存池支持自己手动 alloc/free：

```text
(lldb) run -i
```

程序停在等你输入时，**这不是断点**，是程序在 `scanf` 等键盘。  
你照常输入即可，例如：

```text
a 100
d
f 0
q
```

如果想「一点击分配就停」，可以：

```text
(lldb) b pool_alloc
(lldb) run -i
```

然后输入 `a 100`，回车后就会停进 `pool_alloc`。

## 5. 常见小白问题

### Q1：我说 `b pool_alloc`，它说找不到？

常见原因：

1. 没有重新 `make`（旧程序没有符号）
2. 函数名写错（大小写要完全一样）
3. 那个函数被写成了 `static`，一般 **仍然能断**；若不行，用行号：`b mempool.c:272`

### Q2：`run` 一下就跑完了，根本没停？

说明 **断点没命中**。比如你断在 `block_coalesce`，但这次演示路径没走到合并。  
解决：多下几个断点，或先 `b main`，再一步步 `n`/`s` 跟。

### Q3：`p cur` 显示一长串地址，看不懂？

指针本身就是地址。想看「里面的内容」要用：

```text
(lldb) p *cur
```

结构体字段也可以：

```text
(lldb) p cur->size
(lldb) p cur->is_free
```

### Q4：程序崩溃（segmentation fault）怎么查？

先正常启动再跑：

```text
(lldb) run
```

崩的时候 lldb **通常会自动停在出事附近**。然后：

```text
(lldb) bt          # 看崩溃前调用链
(lldb) f           # 看当前行
(lldb) p 可疑变量
```

很多野指针、越界，就是这样逮到的。

### Q5：`n` 和 `s` 到底用哪个？

- 对「库函数 / 已经懂的函数」：用 **`n`**，别钻进去浪费时间  
- 对「你正在学的函数」（比如 `block_split`）：用 **`s`** 走进去看细节

## 6. 和 gdb 的对照（以后看到教程不慌）

| 含义 | lldb | gdb（概念相同） |
|------|------|-----------------|
| 断点 | `b 名字` | `break 名字` |
| 运行 | `run` | `run` |
| 下一行 | `n` | `next` |
| 步入 | `s` | `step` |
| 继续 | `c` | `continue` |
| 打印 | `p x` | `print x` |
| 栈 | `bt` | `backtrace` |
| 退出 | `q` | `quit` |

网上很多「gdb 教程」把命令换成上表左边，在你 Mac 上基本都能用。

真要装 gdb：

```bash
brew install gdb
```

但入门阶段 **没必要**，lldb 完全够。

## 7. 一张「作弊小抄」（贴显示器旁边）

```text
lldb ./mempool          # 启动
b block_split           # 断点
b block_coalesce
run                     # 跑
n / s                   # 单步
p *b                    # 看块头
p b->size
bt                      # 我在哪
c                       # 继续
q                       # 退出
```

## 8. 练习任务（做完就算会了）

1. 在 `pool_alloc` 打断点，`run`，第一次停下时看 `n`（要分配的大小）是多少。  
2. 单步进 `block_split`，对比分裂前后 `b->size`。  
3. 在 `pool_free` 打断点，看释放 `b` 后，中间那块 `is_free` 是否变成 1。  
4. 释放 `a` 时停在 `block_coalesce`，看左边/右边有没有被合并，`size` 有没有变大。

做完这 4 条，你就已经会「真正用调试器看指针和链表」了，比只看 `printf` 强很多。

## 附：在 Cursor 里点红点调试（可选）

不想敲命令也可以：

1. 打开 `mempool.c`  
2. 行号左边点一下，出现红点 = 断点  
3. 左侧「运行和调试」→ 选用 **lldb** 启动  
4. 上方出现继续 / 单步按钮，左侧能看变量  

命令行版和图形版是同一套思想：**断点 → 跑 → 看变量 → 单步**。  
建议先把上面命令行走通一遍，图形界面只是按钮版。
